# 독립 운영과 복구

최초 설치의 OS·도구·하드웨어·OpenStack·네트워크 조건과 명령은 [설치 방법·환경 조건·서버 사양](installation.md)을 참조합니다.

## 구성과 분리

활성 진입점은 `platform/server/community-bootstrap.js`입니다. 전용 환경파일을 읽고 DB를 검사한 뒤 동일 디렉터리의 플랫폼 API를 실행합니다. 부모 Terminal Lab 소스를 import하거나 부모 `.env`·clouds.yaml·DB를 검색하지 않습니다. 기존 `users`가 있지만 Community 마이그레이션 표식이 없는 DB는 거부합니다.

공통 사용자·관리자 쿼리와 백업 형식을 유지하기 위해 원본 스키마와 빈 교육 호환 테이블을 사용합니다. 교육 콘텐츠 시딩은 실행하지 않으며 교육 화면·HTTP 진입점은 제외합니다. 공유 모듈의 교육 호환 코드와 테이블을 완전히 제거한 별도 스키마는 아닙니다.

기본 인스톨러는 하나의 앱과 하나의 전용 DB를 구성합니다. 프록시·DNS·메일·OpenStack·Kubernetes·Jenkins 등의 외부 시스템을 자동 설치하거나 기존 서비스를 재설정하지 않습니다.

## 데이터·키

- DB 볼륨: 계정·SSO 연결·OTP·공지·게시판·메시지·설정·자원 요청·감사 기록.
- 앱 데이터 볼륨 `/app/data`: 업로드, 운영 템플릿, SSH known_hosts, 런타임 파일·라우팅 내보내기.
- 상태 디렉터리: `deployment.json`, `app.env`, `database.env`, `initial-admin.txt`, `secrets/`, `backups/`.

`SESSION_SECRET`은 세션뿐 아니라 기존 플랫폼의 암호화 필드에도 필요합니다. `CREDENTIAL_KEY`는 0.1 코어 데이터 전환에 사용합니다. 두 키와 OAuth/메일 등의 서버 설정을 데이터와 함께 보호하세요. 업데이트 때 키를 재생성하지 않습니다. 앱·DB 볼륨이 사라지면 빈 볼륨을 자동 생성해 운영하지 않습니다.

## 백업·복원

`backup`은 앱을 잠시 중지하고 동일 시점의 `community-*.dump`와 `community-*.files.tar.gz`를 만듭니다. 앱이 실행 중이었다면 백업 후 다시 시작합니다. 별도로 `app.env`·`database.env`·`deployment.json`·`secrets/`도 보호된 장소에 복사합니다.

복원은 운영자가 설치 ID·컨테이너 이름·대상 볼륨·백업 쌍을 확인한 후 수행합니다. 대상 Community 데이터가 덮어써집니다.

1. 현재 백업을 확보하고 앱을 중지합니다. DB는 실행 상태로 둡니다.
2. `deployment.json`의 `database` 컨테이너를 대상으로 `podman exec -i <community-db> pg_restore -U community -d community --clean --if-exists --no-owner < community.dump`를 실행합니다.
3. 같은 설치의 `data_volume` 내용에 대응하는 파일 백업을 복원합니다. 앱 이미지의 `tar`를 일회용 컨테이너에서 사용하며, 반드시 이 설치의 볼륨 이름을 확인합니다.
4. 백업 시의 동일 키·설정으로 앱을 시작합니다. 로그인·SSO·OTP·게시판·자원 기록을 확인합니다.

Docker는 위 명령의 엔진을 바꿉니다. DB 복원은 실제 OpenStack 자원을 과거로 되돌리지 않습니다. 복원 후 자원과 기록을 대조합니다.

## 0.1 코어 배포에서 전환

이 분리 작업 중 만들어진 0.1 코어 DB 표식이 있다면 계정·프로젝트 요청·클라우드 작업·플랫폼 설정을 0.2 플랫폼으로 가져옵니다. 암호화된 VM 접속정보는 원래 키로 해독한 뒤 플랫폼 방식으로 다시 암호화합니다. 세션은 만료되어 다시 로그인해야 합니다. 이전 감사 로그·공개 라우팅 원본 테이블은 보존하며, 공개 라우팅은 새 플랫폼 설정에서 다시 등록해야 합니다.

0.1 → 0.2 스키마 전환은 이전 앱으로 즉시 되돌릴 수 없습니다. 업데이트 실패 시 앱을 중지한 상태로 두고 DB·백업을 보존합니다. 이전 앱을 사용하려면 전환 전 DB 백업과 해당 앱 이미지를 함께 복원합니다. 그 외 업데이트 실패 시 이전 이미지 재시작을 시도하지만 DB를 자동 복원하지 않습니다.

설치 단계가 `prepared`인 상태에서 이미지 다운로드나 빌드가 실패하면 `resume`으로 원래 키를 유지해 재시도합니다. 기존 운영 설치에는 `start`나 `update`를 사용합니다.

## 확인 범위

새 PostgreSQL에서 계정·관리자 권한, 공지·일반 Q&A, 랩보드 화면·API 제외, Google/Kakao/Naver SSO 응답 대역, OTP 등록·로그인, 교육 API 차단을 시험합니다. 실제 OAuth 등록·SMTP 발송·OpenStack/CAPO/Jenkins 연결 및 Linux 컨테이너의 설치·업데이트·백업 복원은 운영 대상 환경에서 추가 검증해야 합니다.

0.2.1은 랩보드 서비스를 실행하거나 기존 보드 파일을 읽지 않습니다. 기존 앱 데이터 볼륨의 보드 파일은 보존하며 백업에는 포함될 수 있습니다. 소스 배포 ZIP에는 운영 데이터가 들어가지 않습니다.
